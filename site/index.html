From a typical agent repo to an enterprise blueprint

Most published "AI project structures", such as Poornachandra Kongara's widely shared "Enterprise AI Project Structure File Tree" infographic, describe one agent application repository: agents, prompts, tools, RAG, memory, evals and a deploy folder. That is a sound start. It is not yet an enterprise blueprint. An enterprise blueprint has to serve many teams, several clouds and several industries, and it has to carry the governance evidence that auditors and regulators ask for.

How it relates to The Architect's ML Playbook: a typical agent repo covers the GenAI runtime only. The ML Playbook covers 30 classic and deep-learning algorithms with Concept, Build and Production labs. This blueprint puts both under one roof: the agent runtime in platform/core, classic models in platform/ml, and one governance, observability and ARB layer over both.

What a good agent repo already has keep

  • Prompts as versioned assets in a registry.
  • Agents with prompt and config next to code.
  • A tool registry and MCP servers in one allow-listed place.
  • Guardrails, PII redaction and audit logs.
  • Golden datasets wired into CI as a quality gate.
  • Tracing of cost, latency and errors per agent.
  • Architecture decision records.
  • Model choice in config, with fallbacks.

What an enterprise adds add

  • Cloud adapters: a cloud-neutral core with AWS, Azure and Google Cloud specifics kept apart.
  • LLM gateway: one place for routing, quotas, keys, cost and a kill switch.
  • Risk tiers and an AI inventory: a register of every AI system and its risk level.
  • Control mapping: NIST AI RMF, ISO/IEC 42001, EU AI Act, OWASP, sector rules.
  • Data contracts, classification and lineage for what feeds RAG and prompts.
  • Security: threat models, red-team sets, agent identities.
  • FinOps: budgets, cost per transaction, chargeback.
  • Industry packs: reusable use cases, guardrails and evals per sector.
  • Human approval and incident runbooks.
  • System cards and model cards per AI system.

Three structural changes change

  • Policies are owned centrally and consumed by each repo, so delivery teams cannot quietly edit them.
  • CI runs a policy gate next to tests and evals: is the tier approved, the model on the approved list, the system card present?
  • Infrastructure code has one module per cloud behind a common interface.

Simple way to remember the difference: an agent repo is a well-built house. The Enterprise AI Architecture Blueprint is the town plan: zoning rules (governance), shared utilities (gateway, observability), building codes per district (industry packs) and an inspector (the AI ARB).

Illustrative example

Regional insurer, Azure shop. Claims wanted a claims-summary assistant, Underwriting wanted submission extraction, IT had already built a ChatGPT-style internal bot. With the blueprint in plug-in mode, the existing bot was routed through the LLM gateway and given tracing and a model card in two weeks. Design principles

  1. Cloud-neutral core, thin adapters. Swap Bedrock for Foundry without touching agents.
  2. Policy as code. Rules are tested and versioned like software.
  3. Evidence by default. Every run leaves a trace an auditor can read.
  4. Risk-proportionate. A marketing copy tool does not get the same review as a credit decision tool.
  5. Human in the loop for consequential actions.
  6. Reuse before build. Patterns and domain packs first.

How the adapter works

Agents call gateway.complete(model="reasoning-large", ...). The adapter reads models.yaml and maps that alias to a real model on the chosen cloud. Agents never import a cloud SDK directly.

Same model, any cloud

Several model families are offered on more than one cloud (for example, Claude is available on Bedrock, Foundry and Vertex AI). Choosing a cross-cloud model for an alias keeps one prompt library portable, which makes the exit test cheaper.

Illustrative example

Distributor on AWS acquires a company on Azure. Both run the kit. Year one: each keeps its cloud; reports, ARB and AI inventory are shared because the governance layer is identical.

Day-0 steps

  1. Charter and sponsor. One page: purpose, scope, decision rights. Signed by a C-level sponsor.
  2. Risk tiers. Define Tier 1–3 and the controls each requires.
  3. Pick one primary cloud. Use the existing enterprise agreement and landing zone.
  4. Stand up the shared platform. Gateway, guardrails, tracing, prompt registry.
  5. Run two lighthouses. One internal (low risk), one customer-facing (medium).
  6. Publish results. Cost, quality, time saved. Use them to fund scale.

Plug-in steps

  1. Discover. Survey teams, scan expense reports and network logs for AI SaaS.
  2. Register. Put every system in ai-inventory.yaml with an owner.
  3. Tier. Assign each a risk tier; high-risk first.
  4. Wrap, don't rewrite. Point existing apps at the LLM gateway; add tracing and output guardrails.
  5. Back-fill evidence. Model card, golden eval set, ARB record.
  6. Retire duplicates. Three chatbots doing the same job become one.

Illustrative example (plug-in)

Mid-size bank. Discovery found 23 AI tools, 9 unknown to IT. Four touched customer data with no logging. Within 8 weeks those four were behind the gateway with PII redaction; two were retired; the rest got model cards. When examiners next asked what AI the bank ran, the inventory gave them a single starting document.

  1. Name the regulated decisions. Which outcomes affect a person's money, health, safety, job or rights? Those are Tier 3 by default.
  2. List sector regulators and rules with Legal. Map each to a blueprint control in control-maps/.
  3. Classify sector data (account, policy, patient, citizen, OT telemetry) into the blueprint's four data classes.
  4. Write sector guardrails: what AI must never say or do here.
  5. Collect golden examples from front-line experts, 100–300 per use case.
  6. Pick 3–5 starter use cases from the Pattern ranking and publish the pack.

Use case walkthrough: financial services

Fee dispute explainer (AIS-003) for a retail bank. This tab follows one use case through every folder of the project structure: who touches which file, in what order, and what happens at runtime. Every file named here is in the repository, so you can open it as you read.

Illustrative example. "Example Bank" is fictitious. The files, contract, guardrails and tests are real and run; the bank, people and numbers are a composite for teaching.

The story

At 9:02 pm, Maria sees a $35 overdraft fee in her mobile banking app. She wants to know why it was charged and whether she can get it back. Today she would call, wait, and get an answer that depends on which agent picks up. With AIS-003, the app explains the fee from the published fee schedule, checks her fee history, and opens a refund request. A staff member approves it the next morning. The agent cannot refund more than $50, cannot close her account, and cannot give investment advice, whatever anyone types.

WHAT

An in-app chat agent that explains fees from the fee schedule and opens refund requests of up to $50, each approved by a person.

WHY

Fee questions are a top call driver. Wrong fee information is a UDAAP risk, and refund decisions are inconsistent between agents.

WHO

Sponsor: head of retail digital. Owner: retail-banking-ai. AI ARB approves. Model risk validates. Operations staff approve refunds.

WHEN

Tier 2 at L2: ARB review at design and at release, a 6-week pilot, and re-approval before the contract expires on 2027-06-30.

WHERE

The mobile app channel. It runs on the primary cloud set in kit.yaml (Azure here), with a tested exit to AWS.

HOW

A conversational agent, plus RAG over the fee schedule, plus tools under an agent contract, plus a human approval queue.

Use case walkthrough: insurance

Underwriting manual assistant (AIS-001) for a commercial insurer. This tab uses the same project structure as the bank example, for a different shape of AI: an internal RAG assistant at L1, with no write tools. It shows the blueprint scaling down as well as up. Lab 02 runs this business case.

Illustrative example. "Example Mutual" is fictitious. The files, golden cases and guardrails are real and run; the insurer, people and numbers are a composite for teaching.

The story

At 4:30 pm, Dev, a commercial underwriter, is quoting a delivery company's fleet. One driver had a DUI conviction three years ago. The answer is somewhere in a 600-page manual. Dev asks the assistant and gets the rule with its citation: "Commercial Auto Guide CA-5.1: drivers with a DUI conviction in the past 5 years are not acceptable. The account may be written only if that driver is excluded by endorsement." Dev, not the assistant, decides. The assistant never binds, prices or declines, and it only answers from documents Dev's groups may read.

WHAT

An internal assistant that answers underwriters' questions from the underwriting manual and appetite guide, with citations.

WHY

Manuals are long and change often. New underwriters are slow, and appetite gets misread. The NAIC AI model bulletin expects a governed AI program.

WHO

Sponsor: chief underwriting officer. Owner: underwriting-ai-team. AI ARB approves. A senior underwriter reviews a weekly 2% sample.

WHEN

Tier 2 at L1, pilot status. Retire it if the eval pass rate stays below threshold for two consecutive weeks.

WHERE

Inside the underwriting workbench (internal only). The manual is indexed from the document management system.

HOW

The RAG pattern with permission-aware retrieval, an approved prompt version, a grounding check and the insurance pack's guardrails.

    Agent contracts: executable, enforced, auditable

    The model proposes. The contract defines obligations. An independent execution layer enforces them. New in v1.1: every agent at autonomy L2 or above runs under one machine-readable contract that binds the whole stack, not one checkpoint.

    WHAT

    One contract per agent: planning, models, data classes, memory, tools, delegation and execution limits.

    WHY

    An agent cannot enforce its own boundaries. The architecture must block and audit unauthorized actions when models fail or instructions conflict.

    WHO

    Owner drafts, AI ARB approves (ARB id in the contract), platform runs the enforcer, audit reads the evidence.

    HOW

    Approve one plan per task; run each approved step once; authorize every step against the live contract; narrow and share one budget on delegation; record four kinds of evidence.

    AuthorizationWho allowed it, under which rule?Allow or deny, contract id and version, rule, approver
    ExecutionWhat actually happened?Done, queued or failed; output hash; approval id
    Failure modeWhat stops it
    A retrieved note says "ignore refund limits"Authority is read only from the contract; the $500 refund is refused
    The model acts outside its approved planEach step must match an approved step
    A sub-agent asks for more than its parent hasDelegation only narrows: intersection of permissions, tighter limits
    An incident needs one agent stopped nowRevoke the contract; running tasks stop at their next step
    The model replays an approved refund, or re-plans mid-taskEach approved step runs once; one plan per task
    A step labelled "explain fee" tries to delegateEach intent lists exactly which tools, models, memory or delegates it may use
    Sub-agents fan out to multiply limitsCost and tool calls are counted once across the delegation chain
    A queued refund is approved after the contract is revokedApprovals go through the enforcer, which re-checks the contract and records the approver
    Amount is NaN, negative or missingRefused; malformed steps are recorded as denials, never as allows
    Someone edits, deletes or cuts off audit recordsThe hash chain fails; an anchor stored outside the runtime detects truncation

    Honest limit: the reference enforcer runs in-process so the lab works anywhere. In production, run it as its own service in front of tools, models and memory, so agents have no path around it. 42 tests cover these failure modes (tests/test_contracts.py); they were added after an independent adversarial review of the first draft.

    EA must-do 1 · AI strategy and portfolio

    WHAT

    Link AI to business capabilities, then run AI ideas as a scored portfolio.

    WHY

    Most AI spend fails because it chases demos, not capabilities with measurable outcomes.

    WHO

    EA leads; business unit heads, CFO office and CIO decide.

    WHEN

    Before the first build; refreshed every quarter.

    WHERE

    00-strategy/ and the EA repository tool (e.g. LeanIX, Ardoq, Sparx).

    HOW

    Capability heat map → idea scoring → build / buy / partner decision → funding.

    1. Map capabilities. Mark which business capabilities AI can lift (e.g. "Claims adjudication", "Supplier onboarding").
    2. Collect ideas through one intake form, not email.
    3. Score each idea 1–5 on value, feasibility (data ready? pattern exists?), and risk.
    4. Decide build, buy or partner. Copilot features in SaaS you already own often beat a custom build.
    5. Rationalize. Find duplicate AI tools in the application portfolio and retire them (TIME model: Tolerate, Invest, Migrate, Eliminate).
    6. Publish a roadmap with lighthouse, scale and retire waves.

    Illustrative example

    Capital-markets firm received 140 AI requests in one quarter. Scoring cut that to 8 funded items. Three were met by switching on features in existing vendor platforms, saving a custom build.

    EA must-do 4 · Data and security architecture for AI

    WHAT

    Decide which data may reach which model, and how agents are identified and limited.

    WHY

    AI turns data leaks into conversation leaks, and agents can act, not just read.

    WHO

    EA with CDO, CISO and Privacy.

    WHEN

    Before any RAG index or tool goes live.

    Data checklist

    • Classification → model matrix (restricted data only to private endpoints).
    • Data contract per RAG source: owner, freshness, quality rules.
    • Document-level access control carried into retrieval.
    • Lineage from source document to answer citation.
    • Retention rules for prompts, outputs and memory.
    • Data residency and sovereignty: which regions each model endpoint may run in.
    • Synthetic or masked data for dev and test; no production data in sandboxes.

    Security checklist

    • Threat model each use case against OWASP LLM Top 10.
    • Prompt-injection defenses on all retrieved and tool content.
    • Each agent has its own non-human identity and least-privilege scopes.
    • Write or payment actions require human approval.
    • Red-team suite runs in CI and before each major release.

    Illustrative example

    Bank HR-policy bot answered a branch employee's question using an executive compensation document, because retrieval ignored SharePoint permissions. Fix: carry user identity into the retriever and filter by document ACL. Now a standard in the blueprint's knowledge/retrievers.
